# Job_Intel_Agent

采集公开招聘数据 → 结构化抽取 → 与简历比对 → 输出「该投哪家 / 我缺什么」。

## 这个项目解决什么问题

求职时面对几十上百个岗位，靠人眼看 JD 效率极低。而市面上的「AI 求职助手」大多只是关键词匹配，回答不了真正的问题：**这个岗位我到底缺什么**。

这个项目把这条链拆成四步，每一步都用可验证的方式实现：

1. **采集**：从公司招聘官网自身调用的公开接口拉真实 JD（当前 7 家公司、1000+ 条）
2. **抽取**：用 LLM 把非结构化 JD 变成结构化要求（技能 / 年限 / 学历 / 职责）
3. **匹配**：简历画像与岗位要求逐项比对，输出**技能覆盖度 + 具体缺口**
4. **追踪**：记录实际投递与回复，用回复率验证系统是否真的有用

## 效果

单条岗位的输出长这样（脱敏）：

```
AI Agent开发工程师 — 深圳
  技能覆盖：82%
  缺口：
    - 高并发高可用分布式系统的生产级设计与压测
    - 异步任务调度框架（Celery / Temporal）的实战
    - 长任务运行时与执行沙箱的隔离方案
```

跨岗位的聚合输出直接回答「最该补什么」：

```
Go 语言开发      40 次
Java             25 次
C++              13 次
消息队列           7 次
```

## 数据来源与合规

只访问公司招聘官网**自身页面会调用**的公开接口：

| 公司 | 接入方式 |
|---|---|
| 字节跳动 | `jobs.bytedance.com` |
| MiniMax / 百川智能 / 零一万物 / 面壁智能 / 智谱 AI | `*.jobs.feishu.cn` |
| 商汤科技 | `hr-jobs.sensetime.com`（自定义域名，同一套 ATSX 后端） |

自我约束：

- **严格串行**，两次请求间隔 ≥ 3 秒，绝不并发
- 响应全量归档（按采集日期分目录），只拉增量
- 只取公开岗位信息，**不碰任何候选人个人信息**
- 原始 dump 不进仓库（`data/` 已忽略），报告保留原始 URL 归属
- 明确不做：Boss / 拉勾 / 猎聘等有反爬与 PIPL 风险的平台

## 快速开始

```bash
pip install -r requirements.txt

# 1. 采集（先小批量看数据）
python -m collectors.run --company bytedance --keyword Agent --max-pages 2

# 2. 看库里的数据
python scripts/inspect_db.py --stats

# 3. 生成简历画像
python scripts/build_profile.py

# 4. 匹配 + 报告
python scripts/match_jobs.py -n 10      # 先跑 10 条试水
python scripts/match_jobs.py            # 全量候选池

# 5. 记录投递
python scripts/applications.py add --company bytedance --title "..." --url "..."
python scripts/applications.py stats
```

## 设计上的几个关键决定

**1. 业务主键 = 公司 + 可选城市集合 + 标题**

实测发现同一岗位的 `source_id` 会变（正文一字不差，id 却不同），所以 `source_id` 只能标识「一次发布」，不能标识「一个岗位」。跨批次识别同一岗位只能用业务主键。

**2. 近似去重必须「先分组、再比正文」**

不分组时，同一公司所有 JD 套同一份模板，不同产品线的岗位会被判成重复（实测 100 条里误杀 13 对）。现在按业务主键开桶，桶内才比 SimHash。

**3. 经验年限不作为硬门槛**

「0 年全职经验」和「什么都不会」是两回事。`min_years` 不参与筛选也不扣分，只作为一句说明——否则会漏掉大量「写 3 年但实际接受优秀应届」的岗位。

**4. 抽取结果按内容指纹缓存**

同一条 JD 在调 prompt、重跑流程时会被抽很多次。缓存让重跑接近零成本，而 JD 内容变化时指纹自动失效。

**5. 没套 LangGraph**

这是批处理管线，不是需要状态机、条件跳转、人工中断的交互式 Agent。套上只会多一层无意义的抽象。

## 局限

- **候选池偏向单家公司**：目标城市（深圳/广州/佛山）的 AI 岗位 93% 来自字节，缺口统计仍是「一家公司的偏好」而非行业共识
- **社招池**：`portal_type=6` 是社招，校招 / 实习岗位需要换入口
- **匹配分是 LLM 给的**：同一岗位多次运行分数可能略有波动，适合排序，不适合当精确指标
- **没有做检索**：候选池只有百余条，直接全量打分；数据量上千后需要引入向量检索
